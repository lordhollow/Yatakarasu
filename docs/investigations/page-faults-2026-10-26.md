# Yataの継続的なページフォルト調査

調査日: 2026-10-26（JST）。対象は1280×800、.NET Framework版Yata。

## 結論

主因として再現できたのは、`WidgetContainer.Draw()`でARGB形式の全画面ビットマップ3枚を繰り返し合成する処理。
3層の形式を`Format32bppPArgb`へ変更すると、単独再現試験のページフォルトはほぼ消えた。
`DrawImageUnscaled()`への変更や`Graphics`の生成頻度の変更だけでは、この現象を解消しない。

GDI+のアルファ合成時の一時変換領域に整合する結果であり、増え続ける累積値をそのままメモリリークやページファイル読み込みと解釈するのは適切ではない。
ただし、実行中Yataの呼び出しスタック別内訳は採取しておらず、HW取得やWinForms内部の寄与まで全量を説明したわけではない。

## 実プロセスの観測

18:44:36～18:45:04 JST、21標本、カウンター時刻差27.57秒。
サンドボックスではホストのプロセスを列挙できないため、ホスト側の読み取り権限でWMIの累積カウンターを取得した。
Yataの停止・再起動や設定変更は実施していない。

| 項目 | 観測値 |
| --- | ---: |
| Yataのページフォルト | 38,121回/秒 |
| CPU使用率（1コアを100%とする） | 10.37% |
| Private Bytesの変化 | +824 KiB |
| Working Setの変化 | +28 KiB |
| プロセスのRead/Write Bytes累積値の変化 | どちらも0 |
| システム全体のPage Reads/sec平均 | 1.52 |
| システム全体のPages Input/sec平均 | 5.52 |
| 利用可能物理メモリの最小値 | 32,753 MiB |

大量のページフォルトに対してディスク読み込みは少なく、主にソフトフォルトと考えられる。
システムのカウンターは全プロセスを含み、プロセスのI/Oカウンターもハードフォルトそのものを数えるものではないため、Yata単独のハードフォルト数とは断定しない。
この短時間の観測だけで、長時間のメモリリークまで否定するものでもない。

ページフォルトの区別は[Microsoftの解説](https://techcommunity.microsoft.com/blog/askperf/the-basics-of-page-faults/373120)を参照。

## 描画だけの再現試験

`tools/diagnostics/GraphicsPageFaultProbe.cs`で、HW監視を開かず、同サイズの3層を描画した。
各ケース30回のウォームアップ後に200回×3組を測定した。`Graphics`生成のみのケースは1000回×3組。
描画ケースの測定区間ではGen0/Gen1/Gen2のGCはいずれも0回だった。
数値はこのPC・この描画先での結果であり、フレームレートや時間の保証ではない。

| ケース | ページフォルト/回（平均） | 所要ms/回（平均） |
| --- | ---: | ---: |
| 現行ARGB 3層 + DrawImage | 3006.002 | 10.382 |
| ARGBの背景1枚 | 1002.003 | 2.566 |
| 完全透明ARGBのオーバーレイ1枚 | 1002.002 | 2.290 |
| ARGB 3層 + DrawImageUnscaled | 3006.000 | 10.631 |
| ARGB 3層 + ピクセル矩形を明示 | 3006.040 | 10.617 |
| PArgb 3層 + DrawImage | 0.0017 | 6.916 |
| PArgb 3層 + DrawImageUnscaled | 0.0017 | 7.259 |
| Graphicsの生成・破棄のみ | 0.016 | 0.00045 |

1280×800×4バイトは約1000個の4 KiBページに相当し、1枚あたり約1002フォルトという実測と対応する。
3層を毎秒10回合成すれば、それだけで約3万フォルト/秒となる。実Yataの約3.8万フォルト/秒の大きな部分を説明できる規模。
完全透明でも変換が発生しており、`DrawImageUnscaled`だけへの変更では改善しなかった。
PArgbでのアルファ合成の効率については[MicrosoftのWinForms最適化記事](https://learn.microsoft.com/en-us/archive/msdn-magazine/2006/march/practical-tips-for-boosting-the-performance-of-windows-forms-apps)も参照。

## 対応と検証

`WidgetContainer.Initialize()`の背景・明るさ・ウィジェットの3層を`Format32bppPArgb`で生成するよう変更した。
描画座標・更新間隔・HW監視設定は変更していない。
従来のARGB形式との半透明合成の比較を回帰テストに追加し、明るさ1/0.45/0、半透明の重なりと文字を検証する。
RGBの差は乗算済みアルファの量子化を考慮して各成分2まで、出力アルファは一致を要求する。

実行中のYataは旧形式のままなので、実アプリでの改善量は両プロセスを再起動してから比較する必要がある。
通常利用するReleaseを再ビルドして再起動後、同じ表示状態で以下を採取する。試験ビルドは`tests/bin/`に分離してある。

```powershell
./tools/diagnostics/measure-process-page-faults.ps1 -DurationSeconds 30
./tools/diagnostics/run-graphics-page-fault-probe.ps1
./tests/run-configuration-tests.ps1 -Configuration Release
```

採取スクリプトはCSVと`.summary.json`を`tests/bin/PageFaultInvestigation/`に出力する。
管理者で実行中のYataでもWMIから読み取れる範囲を採取し、プロセスの動作や設定は変更しない。
もし修正後も大きな残差があれば、描画回数・HW機器別更新を分けた計測、またはWPR/WPAでスタック付きのメモリトレースを追加する。

## 追補: PArgb適用後に残る約1万フォルト/秒

利用者が描画に問題がないことと発生数の減少を確認した後、再起動済みのYataを再計測した。
12秒指定、13標本、カウンター時刻差11.54秒で10,581フォルト/秒だった。
Private Bytes・Working Set・Read/Write Bytesの差はいずれも0。CPUは1コア換算7.58%、システム全体のPages Input/sec平均は2.23。

残る主要因として、WinFormsのダブルバッファの再確保を再現できた。
この環境の`BufferedGraphicsManager.Current.MaximumBuffer`は既定で225×96。
1280×800はその上限を超えるため、一時的な描画バッファをフレームごとに確保・破棄する。
上限を超えるバッファを保持しない動作は[MaximumBufferの仕様](https://learn.microsoft.com/dotnet/api/system.drawing.bufferedgraphicscontext.maximumbuffer?view=netframework-4.8.1)にも記載されている。

`run-graphics-page-fault-probe.ps1 -WindowBuffers`で、同じPArgb 3層をWinFormsの`WM_PAINT`経路へ渡して比較した。
各ケース30回ウォームアップ後に200回×3組を測定し、各組で実際に230回の`OnPaint`が呼ばれることを確認する。
ウィンドウは画面外に置き、空の`BeginPaint`クリップによる描画省略を避けるため、対象ウィンドウのDCを明示して全クライアント領域を描画する。

| ケース | ページフォルト/フレーム（平均） | 所要ms/フレーム（平均） |
| --- | ---: | ---: |
| WinForms・既定の保持上限225×96 | 1002.362 | 3.807 |
| WinForms・保持上限1281×801 | 0.005 | 2.831 |
| BufferedGraphicsの直接呼び出し・既定上限 | 1002.005 | 3.804 |
| BufferedGraphicsの直接呼び出し・保持上限拡大 | 0 | 2.746 |

全ケースで測定中のGCは0回。約1002フォルト×毎秒10フレームは約1万フォルト/秒で、PArgb適用後の残差の規模と一致する。
当初、画面外ウィンドウへの通常のInvalidate/Updateではダブルバッファ経路のOnPaintが呼ばれなかったため、その試行の数値は採用していない。

`DrawingBuffer.EnsureCapacity()`を追加し、Yataの初期化時およびリサイズ・最小化からの復帰時に、実クライアント領域より1ピクセル大きい上限を確保する。
他のウィンドウ用の大きな上限は縮めない。ダブルバッファ・更新間隔・描画内容は変更しない。
約4 MiBのバッファを再利用する分、常駐メモリが増える場合があるが、毎フレームの確保・初回アクセス・破棄を避けられる。

```powershell
./tools/diagnostics/run-graphics-page-fault-probe.ps1 -WindowBuffers
./tools/diagnostics/measure-process-page-faults.ps1 -DurationSeconds 30
```

今回も実行中Yataは停止・変更していない。通常のReleaseを再ビルド・再起動し、同じ表示状態で実プロセスの改善量を確認する必要がある。
この後にも残る分については、時計などの小画像・テキスト描画やHW取得を切り分ける。

### 小画像とフォーカスの切り分け

`run-widget-page-fault-probe.ps1`を追加し、製品の`AnalogClock`・`SensorCurrentList`・`SensorPlot`・`CommandLauncher`を直接描画した。
HW監視を初期化せず、リストとグラフには12項目・各144履歴の固定センサーを渡す。
時計の実画像168×168のARGB描画だけで28フォルト/回が発生し、PArgb形式では0だった。
製品の時計描画でも同じ28回/描画を再現した。毎秒10回なら約280回/秒に相当する。
文字列24回の描画は0、リストは初期のヒープ拡張後0、グラフは0.02～0.04回/描画で、大量の繰り返しフォルトを再現しなかった。

### 修正と回帰確認

`CommonResource.LoadImage()`で読み込む画像を、ファイルを閉じる前に一度だけ`Format32bppPArgb`へ変換する。
時計・ボリューム・Karasu表示・内蔵アトラス・ファイル指定のアイコンがこの経路を使う。
既定アイコンとページ送り用の生成アイコンもPArgbで保持する。
変換には`SourceCopy`とピクセル単位の同サイズ矩形を指定し、元の透明度とサイズを保つ。

回帰テストでは半透明画像の合成色（RGB各成分差2以内・出力アルファ一致）、ファイルロックの解放、各アイコンの保持形式を確認する。
緑・赤の枠の表示、全フレームでの連続した減衰、最後の消去、待機時の停止を実際の`Click/Update/Draw`で確認する。
別ページの最下段右端、および次/前ページ移動後にフォーカスが残らないことも含める。Releaseの構成回帰テスト19件が成功した。

追加の結合測定では、製品の`WidgetContainer.Update/Draw`による3層合成を、保持上限を確保したWinFormsダブルバッファの`WM_PAINT`へ渡す。
ページ内のランチャーを下端に配置し、緑・赤それぞれ消去まで30フレーム描画する。各組でウォームアップを含む180回の`OnPaint`を検証し、画面外ウィンドウで描画が省略されていないことを確認する。
現在のアイコン設定では、この結合経路も緑枠0.031回/フレーム、赤枠0.011回/フレームだった（3組の平均）。
内蔵アトラス・256px画像・代替アイコンを含む全ケースで最大でも0.059回/フレーム、GCは0回であり、毎フレーム数百～数千回発生する状態は再現しなかった。

### HW取得についての確認範囲

`-OsQueries`ではLibreHardwareMonitorのCPUのOS時間取得とD3D機器情報取得だけを読み取り専用で呼び出す。
この環境のCPU取得は0～0.32回/呼び出し、照会可能な2個のD3Dアダプターは0だった。
これはHW更新全体の試験ではなく、CPUのMSR取得・GPUのベンダーAPI・ストレージ・その他のセンサー更新を含まない。
したがって、静止時の残り約700回/秒まで説明・解消できたとは断定しない。
この先は修正適用後の実測に基づき、実行中プロセスで機器別の更新区間、またはWPR/WPAのスタックを採取して切り分ける。
別の`Computer`を初期化する試験は、機器によってはファン制御の初期化を伴うため、今回の単独測定には使用しない。

### 実プロセス内での機器別計測

新しいドライバー接続や別のComputerを初期化せず、既存の監視処理を計測する`PageFaultDiagnostics`を追加した。
再ビルド・再起動後、右クリックメニューの「ページフォルトを30秒計測」を選ぶ。
操作後はメニューを閉じて通常表示のまま待つ。約30秒後に新規の記録を止め、処理中の機器更新が終わってからCSVを保存する。
保存先は`%LOCALAPPDATA%\Yatakarasu\diagnostics\page-faults-日時.csv`。
通常時は無効でカウンター取得やログ書き込みを行わず、計測を開始しても更新間隔・非同期設定・センサー選択を変更しない。

記録するのは機器IDごとの`hardware.Update()`、センサー履歴の更新、ウィジェット種類ごとのUpdate/Draw、3層合成、画面位置確認。
`process/Total`行は測定全体の増加で、`faults / (elapsed_ms / 1000)`が毎秒の全体値になる。
`scope`行はその区間中に**プロセス全体**で増えた数であり、特定スレッドのフォルト数ではない。
同時に他の計測区間が動いていれば`overlapping_samples`に印を付ける。重複する行の`faults`を合計して全体の内訳として扱わない。
`steady_nonoverlap_samples`と`steady_nonoverlap_faults`は、対象ごとの最初の2回を除外し、他の計測区間と重ならなかった標本だけを集計する。
両者の比で通常の1呼び出しあたりの量を比較できる。ただし、計測していないランタイムの活動などが混ざる可能性は残る。
`HardwareMonitor.Update`は非同期処理を予約する区間であり、機器を実際に更新する`Hardware /...`行と区別する。

回帰テストはDWORDカウンターの周回、初期2標本の除外、別スレッドとの重複、例外時のスコープ解放、処理中区間の待機、期限による自動停止、無効時の停止状態を確認する。
製品のWidgetContainerからUpdate/Draw/合成の記録がつながることも確認し、構成テスト20件・HW監視テスト12件が成功した。
この時点では実行中の旧ビルドへ計測コードを注入していないため、機器別の実測と原因の確定は、このCSVを採取した後に行う。

### NVAPI呼び出し単位の再現

`GraphicsPageFaultProbe.Nvidia.cs`を追加し、使用中のDLLの読み取りメソッドだけを個別に呼び出した。
各5回ウォームアップ後に30回×3組を測定した。
`Computer`や`NvidiaGpu`のコンストラクター、ファン制御の初期化・復元・Closeは呼ばない。
NVAPI/NVMLで機器のハンドルを列挙し、GPU本体は未初期化オブジェクトに読み取り用ハンドルだけを設定する。
この実行経路にファイナライザーがないことも確認している。

| 取得 | 初回試験のフォルト/呼び出し |
| --- | ---: |
| NVAPI GetPowerTopology（電力比率） | 1,176（3組とも同じ） |
| NVAPI GetVoltRailsStatus（電圧） | 249（3組とも同じ） |
| 温度設定 | 0.10～0.23 |
| クロック | 0.167 |
| ファン状態 | 1 / 0 / 0（初期ヒープ拡張を含む） |
| 使用率・温度詳細・メモリ使用量 | 0 |
| NVML消費電力W・PCIe転送量 | 0 |

再試験では電力比率が1,117回、電圧が247回となり、取得時の状態によって量は変動した。
いずれも測定中のGCは0回で、対象2呼び出しのPrivate Bytes差は0。メモリリークと断定する結果ではない。
割り当ての最終的な内部スタックまでは採っていないため、NVIDIAドライバーの特定行の不具合とは断定せず、NVAPI呼び出し経路として原因を扱う。

LibreHardwareMonitorは、画面で使わないセンサーでも、同じ機器のUpdateでは取得する。
[公式0.9.6のNvidiaGpu実装](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/blob/v0.9.6/LibreHardwareMonitorLib/Hardware/Gpu/NvidiaGpu.cs)の`_powers`は`SensorType.Load`の電力比率であり、`SensorType.Power`の消費電力WはNVMLの別経路。
今回の選択設定は使用率・温度・HotSpot・ファン・消費電力Wを使い、電力比率・電圧は選んでいなかった。
NVAPI電力比率の約1,176回が、実プロセスの非重複GPU標本の約1,183回と対応する。

```powershell
./tools/diagnostics/run-widget-page-fault-probe.ps1 -NvidiaQueries -Tag nvidia
```

### 未使用グループだけを省く対応

`NvidiaOptionalQueries`を追加し、使用中の元センサーを確認して、電力比率グループ・電圧を未使用の場合だけ取得対象から外す。
合計・平均の元センサーも含める。グループ内の1個でも選べばグループ全体を復元する。
元のセンサーオブジェクトと配列を保持し、選択変更・対象機器の除外・破棄時に復元する。
現在使用中の温度・使用率・ファン・消費電力Wの取得周期は従来どおり。

ライブラリに公開の取得グループ設定APIがないため、固定している0.9.6.0のNvidiaGpuの内部フィールド`_powers`・`_coreVoltage`へ互換処理を限定した。
型・バージョン・フィールド型・所属センサーを検証し、未知の版や形状には適用しない。
NuGetの参照やライブラリのファイルは変更しない。ライブラリ更新時には互換処理の再検証が必要で、それまでは標準の取得に戻る。
中長期的には、取得グループの選択をライブラリの公開機能として扱える形にするのが望ましい。

実際のライブラリのUpdateメソッドを使い、メモリ内設定と対象2グループのみを与えた単独比較も実施した。
各30回×3組で、取得有効時は1,287.400 / 1,133.200 / 1,119.133回/更新、未使用として省いた後は3組とも0だった。
電力比率を選択すると再び約803回/更新、電圧を選択すると約79回/更新となり、取得の復元も確認できた。
この比較は対象2グループの条件をそろえたもので、機器全体や実行中Yataの修正後の値を測ったものではない。

回帰テストは実ライブラリの型・readonlyフィールドを使用し、未使用時の抑止、片方の電力比率を選択した場合、電圧の選択、合計元の選択、対象機器の除外、元オブジェクトの復元を検証する。
HWやドライバーの初期化はせず、構成テスト21件・HW監視テスト12件が成功した。
通常Releaseを再ビルド・再起動した後、同じ30秒計測で実プロセス全体の減少量とセンサー表示を確認する。
電力比率・電圧を新たに選んだ場合は、必要な取得が戻る分、ページフォルトが増える場合がある。
